RTX 5080 · sm_120 · consumer Blackwell

Flash Attention on a GPU without datacenter features

A hand-written PTX kernel taken from 2.7 to ~183 TFLOPS — and an honest log of what worked, what didn't, and why.

FP16/BF16 · MHA & GQA · D = 64 / 128 · prefill + decode

A from-scratch flash-attention implementation in raw CUDA/PTX for the RTX 5080 (sm_120). Consumer Blackwell lacks the features that make H100/B200 attention fast — no WGMMA, no TMA, no tcgen05/TMEM — so this kernel reaches competitive utilization with only mma.sync, ldmatrix, and cp.async. Optimized step by step from a 2.7-TFLOPS scalar baseline to ~170 TFLOPS at the B=8, S=2048 sweet spot and ~183 TFLOPS peak (≈78% of the 234.8-TFLOPS FP16 roofline), it runs ~1.7× faster than the CUTLASS attention that actually compiles for this GPU. The most useful result is the catalogue of optimizations that didn't help — and the one property that explains all of them.

1The shape of the problem

Attention has two matmuls with a softmax wedged between them: S = Q·Kᵀ, then softmax(S), then O = P·V. The matmuls love tensor cores; the softmax does not. On every KV tile the tensor cores go idle while the softmax runs its exponentials, cross-warp reductions, and barriers. That bubble — not raw FLOPs — is what a good attention kernel fights.

On datacenter GPUs you hide it with hardware: WGMMA (128-thread MMA reading B straight from shared memory), TMA (a DMA engine that copies tiles with zero thread cost), and warp specialization (dedicated load warps overlapping math warps). None of that exists on sm_120. The whole project is: how close to the roofline can you get with only the consumer instruction set?

3Standing up the tensor-core pipeline (v1 → v7)

Before any softmax trick, the kernel had to get onto the tensor cores at all — and then earn the right to do softmax in registers. Three steps did that, and the table above compresses them into one line each. They deserve more, because the third is the hinge the whole project turns on.

v3 — WMMA fragments (2.7 → 26.7). The v1 baseline does both matmuls with FP32 FMAs on the CUDA cores, leaving the tensor cores — which hold far more FP16 throughput than the CUDA-core FP32 path can ever reach — completely idle. (v1's 2.7 isn't near the CUDA cores' own FP32 ceiling either; it's bound by memory and overhead.) The easy on-ramp is NVIDIA's nvcuda::wmma API: declare wmma::fragment operands, load_matrix_sync, mma_sync a 16×16 output tile (the m16n16k16 shape), store_matrix_sync back. It is warp-cooperative — 32 threads jointly own one tile — and it just works. Idle to busy buys ~10×.

The catch is that a fragment is an opaque handle: the API deliberately leaves unspecified which thread and register hold which element. Pointwise work (subtract, exp) can run blind on the fragment, but softmax's cross-thread reductions — the per-row max and sum — need to know which lane holds which score. With WMMA the only supported way to get that is to store_matrix_sync the scores to shared memory and read them back addressably: a full score-matrix round-trip every tile. That round-trip, not the FLOPs, is what keeps the tensor cores stalling between the two matmuls.

v6 — vectorized uint4 loads (→ 38.3). With the cores on, the limiter was not HBM bandwidth — attention reuses each K/V tile from shared memory many times, so its arithmetic intensity is high and the bus is not the ceiling. The limiter was the load path itself: streaming Q/K/V as scalar half issued one narrow global load per element, flooding the load/store unit with instructions and leaving the tensor cores waiting on stragglers. Commit 6438d37 reinterprets each row pointer as uint4 — 128 bits, 8 halves — so one instruction moves 8 elements (VEC_COLS = D_HEAD/8 = 8 loads per D=64 row). The scalar loads were already coalesced and the bytes moved are identical; the win is 8× fewer load instructions, the full 128-bit load width, and more bytes in flight to hide latency. +12 TFLOPS — and the math, the fragments, and the smem softmax round-trip are all untouched.

v7 — PTX mma.sync + ldmatrix (→ 49.2). Swap nvcuda::wmma for inline-PTX mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32, fed by ldmatrix.sync.aligned.m8n8.x2.trans. The direct gain is modest (~+11, plausibly from lower fragment and load overhead — not separately profiled). The real prize is that the register-to-thread mapping is now documented and fixed. For this opcode A is four 32-bit registers (eight halves) and B is two (four halves), and each thread holds its four FP32 outputs at known positions: 

row0 = (lane/4) % 8     row1 = row0 + 8
col0 = (lane % 4) * 2   col1 = col0 + 1

For the first time you know exactly which lane owns which score. That is the precondition for the in-register softmax of §4: the per-row max/sum reduction runs as __shfl_xor_sync across the four lanes sharing a row, and the 16 KB score round-trip disappears (only a 1 KB cross-warp-half exchange remains). The known layout is necessary but not sufficient — §4 is where it's actually spent, taking 49 → 125 — but v7 is what makes that step possible. (ldmatrix.x2.trans has its own trap: lanes 0–7 address the first 8×8 block, 8–15 the second with a +8 offset; getting it wrong is the bug in §4.)

4Keeping the score matrix in registers (v8)

The standard kernel writes S = Q·Kᵀ to shared memory (16 KB), syncs, reads it back for softmax, writes P back to smem, syncs again — two full round-trips per tile. We instead keep S in registers (s_acc[4][4] per thread, 16 values at known MMA positions) and do the softmax there: a shuffle reduction across the four threads that share a row, then a 1 KB cross-warp exchange for the full 64-column max and sum. That single change — deleting the smem_s round-trip and a barrier — took tensor-core utilization from ~18% to ~50% and the kernel from 38 to 125 TFLOPS.

It depends on raw PTX. mma.sync.aligned.m16n8k16 has a known, documented register layout, so each thread knows exactly which (row, col) of S it holds — which is what makes in-register softmax possible at all. ldmatrix loads 8×8 tiles from smem straight into MMA-ready registers. The single hardest bug was its transposed variant: ldmatrix.x2.trans needs threads 8–15 to address the second 8×8 block (+8 cols for K, +8 rows for V); getting it wrong silently loads half the K-dimension and only corrupts the bottom half of the output.

5Direct new-max rescale (v9)

Online softmax tracks a running maximum across tiles. v8 computed exp(S − tile_max) then post-multiplied the sum and the output by exp(tile_max − new_max) to reconcile scales. v9 computes new_max = max(prev_max, tile_max) before the exponential and subtracts it directly, so P = exp(S − new_max) lands in smem already at the right scale — no post-multiply. It removes multiplies from the softmax→P·V critical path and fixes accuracy drift on long sequences.

6Async loads, then occupancy (v10 → v11)

v10 replaced the staged uint4 loads with cp.async: K and V stream gmem→smem without passing through registers, freeing the load/store units for compute and letting the K+V load hide behind a single wait. +13% to 156 TFLOPS.

By v10 the profiler still showed ~54% tensor utilization — the softmax bubble, unhidden. The lever for that is occupancy: more resident thread blocks per SM let the scheduler run another block's matmuls during this block's softmax. We were pinned at 2 blocks/SM by shared memory (37 KB/block against 100 KB/SM). Two changes broke the pin:

Alias P onto K — 37 KB → 28 KB

P doesn't exist while K is in use: it's the softmax output, born after Q·Kᵀ has finished reading K — and there is already a __syncthreads between the last K read and the first P write. So P can reuse K's 9 KB: 

// K is dead after Q·Kᵀ; the phase-3 barrier separates the last
// K read from the first P write, so P safely reuses K's storage.
half* smem_p = smem_k;   // 37 KB → 28 KB  ⇒  2 → 3 blocks/SM

Three lines, output bit-identical, occupancy 33% → 50%. +5 to +9%.

Staged cp.async — hide V behind the softmax

Q·Kᵀ only needs K; V isn't touched until P·V, a whole softmax later. So commit K and V as separate async groups and wait only for K up front, draining V just before P·V (reusing a barrier already there): 

cp_async_commit_group();   // group 1: K
cp_async_commit_group();   // group 2: V
cp_async_wait_group<1>();   // wait K only; V streams behind QK+softmax

Zero extra smem, +1 to +4.5% on top. Combined, v11 is +5 to +15% over v10 — ~170 TFLOPS at the sweet spot, ~183 peak.

7Bigger heads: D=128 and the BN=32 tile

The kernel was secretly generic over head dim — one literal (PV_TILES_PER_WARP = 4) hard-coded D=64. Deriving it as D_HEAD/16 made D=128 work with byte-identical D=64 codegen. But the 64×64 tile that's optimal at D=64 is wrong at D=128: it needs 52 KB → only 1 block/SM. Halving the K/V tile to BN=32 drops it to ~36 KB → 2 blocks/SM (16 warps), worth +28 to +31%. A per-D traits table picks the tile; D=128 now runs on par with D=64 (~72% of peak).

The obvious next step — push to 4 blocks/SM via XOR-swizzled shared memory (to drop padding to 25 KB) plus a 64-register cap — was implemented, verified correct, and lost 4–12%. See §9.

8Running the real models: GQA and BF16

Every modern decoder (GLM-4, Llama-3, Mistral, Qwen, Gemma) uses grouped-query attention — fewer K/V heads than query heads — and ships BF16 weights. The kernel had to handle both honestly, not by faking MHA with replicated KV.

GQA is a pure indexing change: Q/O use the query-head index, K/V use the mapped KV head. The inner compute is untouched; MHA is the special case group = 1. 

// query head h_q reads KV head h_kv (block grouping)
int h_kv = h_q / (num_q_heads / num_kv_heads);

BF16 is a one-type templating. ldmatrix, cp.async, and uint4 loads are all 16-bit/byte-agnostic, so only the MMA opcode and the float→element conversion change: 

if constexpr (is_same<T,__nv_bfloat16>::value)
  asm("mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32 ...");
else
  asm("mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 ...");

The FP16 path stays byte-identical (an interleaved A/B vs the pre-templating commit showed ±0.3%); BF16 accuracy matches FP16 because accumulation is FP32 throughout. Both compile sm_80→sm_120 and validate against an FP64 reference across MHA, GQA (including non-power-of-two groups), and MQA.

9What didn't work

This is the useful part. Every "obvious" speedup below is correct and was rejected on measured numbers — because the kernel is occupancy- and latency-bound, not compute-bound. Cutting math or shared-memory traffic that is already hidden under the tensor cores buys nothing and adds scheduling noise.

Attempted optimizationResultWhy it failed
exp2f fold (log₂e into scale)−2 to −6%the SFU/exp was never the bottleneck; hidden under MMA
Hoist redundant ldmatrix loads−5 to −8%kernel is MMA-bound, not LSU-bound; costs ILP
Pair-scoped bar.sync−22 to −34%full-CTA __syncthreads is hardware fast-pathed
Double-buffered cp.asyncregressed+18 KB pushes over the occupancy cliff (2→1 block)
Swizzle → 4 blocks/SM (D=64)−4 to −12%64-reg cap spills; the 4th block doesn't pay
BN=16 → 3 blocks/SM (D=128)−2 to −12%finer tiling doubles softmax/sync overhead
 The pattern: occupancy gains pay only when they're cheap and you're genuinely under-occupied. The alias win (free, 33%→50%) qualified; pushing further did not.

10Versus CUTLASS on consumer Blackwell

CUTLASS's fast FMHA kernels need WGMMA/TMA (sm_90) or tcgen05 (sm_100) — none on sm_120 — and CUTLASS ships no consumer-Blackwell attention kernel. 12The other phase: decode

Everything above is prefill — full-sequence, compute-bound, tensor-core heavy. Single-token decode (one query row against a long KV cache) is a different kernel entirely: memory-bandwidth-bound, M=1 so no tensor cores, parallelized across SMs by splitting the KV cache (flash-decoding). A group-resident variant that loads each KV head once and reuses it across the query-head group reaches ~99% of HBM bandwidth at long context. That kernel — same GQA/BF16 support — lives separately; it's bound by a different roofline, and "% of peak FLOPS" simply doesn't apply to it. Its own write-up is here: Flash decoding without tensor cores.
