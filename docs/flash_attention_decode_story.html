RTX 5080 · sm_120 · single-token decode

Flash decoding without tensor cores

The other half of attention — one query, a long KV cache, and a ~960 GB/s bandwidth wall.

FP16/BF16 · MHA · MQA · GQA · D = 64 / 128 · split-KV + group-resident

The companion to the prefill kernel: single-token decode. One query row attends to a long KV cache, so M = 1 — no tensor cores, ~1 flop/byte, and the only thing that matters is how fast you can stream the KV cache through the chip. This kernel splits the KV cache across all 84 SMs (flash-decoding) and, for grouped-query models, loads each KV head once and reuses it across its whole query-head group. At long context that reaches ~99% of the RTX 5080's ~960 GB/s HBM bandwidth. FP16 + BF16, MHA / MQA / GQA, D = 64 / 128, validated against an FP64 reference.

1Two phases, two rooflines

Generation has two phases with opposite personalities. Prefill consumes the whole prompt at once — big Q tiles, compute-bound, tensor cores running flat out (that is the other kernel). Decode produces one token at a time: a single query row against the KV cache built up so far. The query length is 1.

That one fact changes everything. S = Q·Kᵀ with M = 1 is a matrix–vector product, not a matrix–matrix one, and the same is true of O = P·V. Arithmetic intensity collapses to roughly 1 flop per byte: every value you read off the bus is used in a couple of multiply-adds and thrown away. The kernel is memory-bandwidth-bound, and the ceiling that matters is the ~960 GB/s HBM bus — not the 234.8 TFLOPS tensor-core peak. "Percent of peak FLOPS" is the wrong yardstick here; percent of HBM bandwidth is the right one.

2No tensor cores, just a stream

mma.sync processes a 16-row tile; with M = 1 it would waste fifteen of every sixteen rows. So decode drops the tensor cores entirely and runs a plain streaming dot-product with an online softmax on the CUDA cores. Per (batch, query-head): load the one Q row, then for every KV position j compute the score q·kⱼ, update the running softmax, and accumulate pⱼ·vⱼ into the output. State is three things — a running max m, a running sum ℓ, and the output accumulator.

The cost is dominated by reading K and V once: 4·B·H_kv·S·D bytes in FP16 (Q and O are a single row each — negligible). The best the kernel can do is bytes / bandwidth, and only if it (a) keeps every SM busy and (b) reads each KV byte exactly once. Those are the two fights, and the rest of this is them.

3Split-KV: filling 84 SMs with one query row

The natural grid is (H_q, B) CTAs. At batch 1 with a handful of heads, that's a handful of CTAs on an 84-SM GPU — the machine sits almost entirely idle, and a bandwidth-bound kernel that uses one SM achieves one SM's worth of bandwidth. Flash-decoding fixes this by splitting the KV cache: the grid becomes (num_splits, H_q, B). Each CTA streams its own chunk of K/V, runs an independent online softmax over it, and writes a partial result — the chunk's max m, sum ℓ, and unnormalized output — to a scratch buffer. A small combine kernel then merges the splits.

The combine is where correctness lives. Each split reports (m, ℓ, O) at its own scale; merging them is a log-sum-exp rescale to a common max. Two guards make it robust: an empty split (whose max never moved off −FLT_MAX) must contribute zero, and an all-empty row must never divide by zero. 

// merge num_splits partials onto a common max
float m = max_i  m[i];
float l = 0, acc = 0;
for each split i:
  // guard 1: an empty split contributes nothing
  float a = (m[i] > -FLT_MAX/2) ? expf(m[i] - m) : 0;
  l   += a * l[i];
  acc += a * O_unnorm[i];
O = (l > 0) ? acc / l : 0;            // guard 2: no divide-by-zero

When the split count is 1 the partial kernel normalizes in place and the combine pass is skipped entirely. The whole plan — split count and chunk size — is computed with deterministic integer math shared by both the scratch-sizing and the launch, so the scratch buffer always matches exactly what the kernel writes.

4One coalesced load per lane

Inside a CTA the thread count is 2·D (so D/16 warps), and the D channels are split contiguously across a warp's 32 lanes: lane l owns channels [l·CH, l·CH+CH) with CH = D/32 (2 at D = 64, 4 at D = 128). That mapping is the whole trick. Each K or V row is read with exactly one vectorized, fully coalesced load per lane — a half2 at D = 64, a uint2 at D = 128. The Q·K dot is a per-lane partial followed by a five-step __shfl_xor reduction across the warp; the P·V accumulate reuses the same per-lane mapping with no shuffle at all. 

// D channels split contiguously across 32 lanes
constexpr int CH = D / 32;              // 2 @D=64, 4 @D=128
dec_loadv(K + j*D + lane*CH, kf);       // one coalesced load per lane
float part = 0;
for (c = 0; c < CH; c++) part += qreg[c]*kf[c];
for (off = 16; off > 0; off >>= 1)       // reduce across the warp
  part += __shfl_xor_sync(-1, part, off);

5Group-resident KV: the real lever

Vectorizing the loads got the bandwidth only partway there. The honest measurement: wider loads on their own were worth +1 to +4%, and at D = 64 they actually regressed. The profiler was clear that load width wasn't the limiter — reading the same KV head many times was. In grouped-query attention, group query heads share one KV head; the per-q-head kernel runs one CTA per query head, and each of them re-reads that shared KV head through L2 (and, once it spills, HBM). That is group× redundant traffic on the one resource decode is bound by.

The fix is to make the KV head resident. The group-resident kernel uses the grid (num_splits, H_kv, B) and assigns one warp per query head in the group. Each K/V tile (TILE_N = 32 rows) is loaded once into shared memory with a uint4-coalesced copy and then reused by all group warps. HBM traffic collapses to the ideal B·H_kv·S·D — each KV byte crosses the bus exactly once. And since each warp owns a complete query head, there is no cross-warp combine: every warp writes its own partial directly.

6The dispatcher: only when it fills the GPU

Group residency isn't free. Collapsing group query heads into one CTA means group× fewer CTAs — which at small batch and short context under-fills the SMs, exactly the regime where the per-q-head kernel (more CTAs) wins. So the launch planner computes both split plans and chooses group-resident only when its grid (num_splits · H_kv · B) reaches roughly the SM count; otherwise it falls back to per-q-head. MQA (group = 1) and very wide groups (> 32) always use per-q-head. The decision is deterministic integer math, so scratch-sizing and launch never disagree.

8GQA and BF16

Grouped-query attention isn't a bolt-on here — the group-resident kernel is organized around KV heads, so GQA is the common case and MHA is just group = 1. The mapping is the same one the prefill kernel uses: h_kv = h_q / (H_q / H_kv).

BF16 is a one-type templating. A Vec2<T> trait picks __half2 or __nv_bfloat162 for the vectorized loads, to_elem<T> handles the float→element store, and the uint4 shared-memory tile copy is byte-agnostic. params.dtype selects it (FP16 by default, so existing callers are unchanged). Validated against an FP64 reference across MHA, MQA, and GQA (groups 3 / 4 / 5), D = 64 / 128, S = 1 … 16384, B = 1 / 3, plus empty-split and adversarial-logit edges — FP16 nrmse ≈ 2e-4, BF16 ≈ 2e-3. 40 registers, 0 spills, compiles sm_80 → sm_120.

9What's left

  • A measured occupancy for the split heuristic. The split count currently assumes 8 resident blocks/SM at D = 64 and 6 at D = 128; replacing that guess with a measured cudaOccupancyMaxActiveBlocksPerMultiprocessor would tighten the plan at the margins.
  • cp.async double-buffering over the smem KV tile. Worth trying only if a config is shown to be latency-bound on the shared-memory load — none currently are, so it stays on the shelf.
  • Short / MQA / D = 64 configs stay launch-bound. That's expected and fine: those kernels are microseconds long and contribute negligibly to real decode, which lives at long context and batched serving — the roofline regime.
